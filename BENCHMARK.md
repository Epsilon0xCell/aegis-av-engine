# Benchmark protocol (publishable, and binding on this project)

This protocol exists so that any performance or detection claim
made for Aegis is checkable, and so that no claim drifts past what
was measured. It follows the honest-claim rules from the project's
competitive research.

## What may be claimed

Only axes this harness measures, on a named machine, OS, corpus and
rule-pack version: scan throughput, scan latency, fixture detection
accounting (TP/FP/FN/TN against generated ground truth),
determinism, and (in the multi-OS CI) verdict consistency across
Windows, macOS and Linux for identical corpus files.

## What may never be claimed

General superiority over any commercial product. Vendor lab scores
(AV-TEST, AV-Comparatives, SE Labs) were produced on real-malware
corpora under lab conditions this project does not reproduce, and
quoting them next to Aegis fixture numbers would be a category
error. Comparisons in this repo are against open baselines run
under identical conditions, or against Aegis's own prior versions.

## Corpus

- Clean corpus: generated files of known provenance
  (aegis/corpora.py), listed in benchmarks/corpus/manifest.json.
- Fixture corpus: synthetic, inert malicious-PATTERN fixtures
  generated from marker strings invented for this project, plus the
  EICAR test file as the standard AV smoke test. No real malware
  is used, stored, or distributed, at any stage.
- The manifest hash is embedded in every benchmark report; a report
  without it is not a result.

## Timing

Cold scan (fresh engine, empty verdict cache) and warm scan (cache
populated) are reported separately, as totals and as files/second.
Single-run teaching numbers are labelled as such; release claims
require at least five runs with median and spread, per OS,
reported per OS, never averaged across operating systems.

## Current local result (teaching run, not a release claim)

See benchmarks/results_local.json, generated by
`python -m aegis.cli benchmark` on the maintainer's Linux machine:
35 corpus files, deterministic verdicts, zero false positives on
the 30 clean files, 4 of 5 fixtures flagged. The one missed fixture
is documented, not hidden: a file of pure random bytes matches no
signature and, as an unknown binary type, draws no heuristic score.
That miss is the honest price of a transparent scorecard, and it is
recorded here so the number can only move by improving the engine.

## Sealed hold-out result (release 1, scored exactly once)

- Commitment: `f1880c8271d7b5003141deb0a8cd6e18c9c321844b0e0c53bbec7036ee6d37c0`
- TP 4, FP 0, FN 1, TN 6 (11 files: mutated fixtures and clean files)
- The one false negative, published verbatim per protocol:
  `holdout_160326_fixture_high_entropy.bin`. Cause: the mutation
  padded the random-bytes fixture with printable text, diluting
  its entropy below the scorecard threshold, and it carries no
  signature. The pure random-bytes fixture was already the
  documented v0.1 miss; this confirms the weakness class rather
  than hiding it. This set is now demoted to the tuning corpus; a
  fresh sealed set will be generated for the next release.

## Correction (2026-11-09, applies to the v1 sections above)

The v1 hold-out false negative was misdiagnosed in the v1 text
above (left unchanged, because rewriting release history would
be worse than the error). The file called
fixture_high_entropy.bin was generated by constructing a fresh
random.Random(3) for every byte, so every byte was identical
and the file's entropy was 0.0, not high. The v1 explanation
("padded with printable text, diluting its entropy") and the
v2 Phase 0 regression framing inherited that misdiagnosis; the
Phase 0 dilution machinery itself is real and separately
tested against genuinely diluted random data. The generator is
fixed, a property test now asserts the fixture's entropy
exceeds 7.0, and the two hold-out sets below replace the story.

## Hold-out release 3 (fixed generator, scored once, verbatim)

Commitment ea45c2d4020054c85b1d6ee190f6dd5c957ae3fdda355158c47795c2926efa85.
11 files. TP 4, FP 0, FN 1, TN 6. This time the fixture is
genuinely random (entropy about 7.95) and the miss is the
engine's standing, deliberate boundary: unknown-format files
are not convicted on entropy alone, because encrypted and
compressed legitimate files are indistinguishable from random
data by that signal. Changing that stance after seeing a
hold-out would contaminate the protocol, so the stance stands
until a separately argued design change earns a fresh set.

## 10,000-file corpus benchmark (local, 2026-11-09)

Corpus: 9,500 generated clean files plus 500 fixtures
(benchmarks/run_10k.py writes the manifest-shaped summary into
benchmarks/results_10k_local.json). 10,000 files, 10,537,934
bytes. Parallel scan (4 workers): 32.21 s, 310.46 files/sec.
Single process: median 1.445 ms per file, p95 7.625 ms. Peak
RSS 53.2 MB. Fixture accounting at scale: 375 of 500 fixtures
flagged; the 125 unflagged are exactly the random-bytes class
named in the release-3 hold-out note. Per-OS release figures
remain the CI-reported ones, per the protocol above.

## v3 Phase 0: measurement integrity (2026-11-09)

Instruments before detectors. Corpus generators now carry a
property registry (aegis/corpus_checks.py): every generated
file's named claim is asserted in CI, and the v2 generator bug,
deliberately reintroduced as a constant-byte fixture, is caught
by claim name in tests. Pack mutation testing
(aegis/packmutate.py) reports a mutation score of 1.0 over
non-equivalent mutants (18 killed, 0 survived, 2 documented
equivalents: single-string all_of/any_of flips). Prevalence
reporting (aegis/prevalence.py) restates precision at 10, 1,
and 0.1 percent prevalence by Bayes adjustment of the same
counts. Per-stage profiling over the generated corpora
(benchmarks/profile_local.json) shows the TLSH and verdict
assembly stage dominating mean scan time (about 3.6 ms of
about 4.1 ms per file on this corpus), which makes lazy
similarity hashing the measured, not guessed, performance
target for the v3 performance pass.

## v3.0.0 release measurements (2026-11-09)

Three-family sealed hold-out, each family generated from the
fixed generators, commitment published before scoring, scored
exactly once: family A (commitment 9a8610d902285e07...) TP 4,
FP 0, FN 1, TN 6; family B (26a2155c95108860...) TP 4, FP 0,
FN 1, TN 6; family C (a06f7a759bc05442...) TP 4, FP 0, FN 1,
TN 6. The worst family is all three: identical accounting. In
each family the single miss is the high-entropy fixture (in
family C, zip-wrapped), the deliberate boundary documented
since v2.0.0: unknown-format files are not convicted on
entropy alone, because encrypted and compressed legitimate
files are indistinguishable by that signal. The stance was
not tuned after scoring.

10,000-file benchmark, same generator and composition as the
v2 run (9,500 clean, 500 fixtures, 10,537,934 bytes): parallel
scan (4 workers) 5.37 s, 1,861.45 files/sec (v2: 310.46);
single-process median 0.187 ms per file (v2: 1.445 ms), p95
0.638 ms; peak RSS 55.1 MB. Fixture accounting identical to
v2: 375 of 500 flagged malicious_pattern, 9,625 clean; the
125 unflagged are the random-bytes class, as documented. The
throughput change is attributed to the lazy-TLSH policy:
measured standalone, the digest costs 2.3 ms per file, and
the corpus is 95% clean files that no longer pay it. Verdicts
on non-clean files are unchanged, digests included.

Five-run small-corpus benchmark (35 files, manifest
a9dfef5f57f34c97): cold median 3,261 files/sec (IQR 152),
warm median 61,257 files/sec (IQR 2,341), deterministic
across runs. Small-corpus cold rates are dominated by fixed
costs; the 10k figures above are the release numbers.

### ClamAV differential (Mode A)

The converted database is generated and the full pipeline is
verified against a stub honouring clamscan's output contract
(agree_detect and agree_clean buckets populated, unexplained
0). clamscan is not installed in the build environment, so no
real-engine comparison is claimed for v4.0.0; the first real
run is a release-checklist item for an environment that has
ClamAV, and the harness reports unavailable status honestly
rather than fabricating buckets.
